# Meister log audit — 21 October 2026

Reviewed all 26 log files found in this checkout: 23 Xcode build/package activity
logs, `build/auto-ship.log`, `build/github-repo-sync/checks.log`, and the local
agent daemon log. Compressed activity logs were decoded before diagnostic
extraction. Seven activity logs were empty. No Meister crash report was present
in the local user/system diagnostic-report directories. A 30-day unified-log
query for Meister processes and the app subsystem returned no records; this
provides no evidence about current on-device behavior.

GitHub lists 16 historical CI runs. All 15 available full logs were read (3,617
lines). The failed May 31 run's raw logs have expired with HTTP 410. Its retained
annotation identifies a missing `DESIGN_REPO_TOKEN` during checkout of the
private design dependency. Eight older successful runs checked only README
existence; the later workflow runs package and Python tests.

## Findings and repairs

| Evidence | Current issue | Change |
| --- | --- | --- |
| Release logs contain repeated missing-key/dependency/profile failures, including failures after archiving | Signing requirements were checked late | Add a local ASC preflight, profile/identity overrides, and prerequisite checks before the build number changes or an archive starts |
| Release logs contain HTTP 403/409 and upload timeouts | ASC requests had no socket deadline; group-assignment handlers swallowed every HTTP error | Bound API calls to 30 seconds, filter explicit build versions directly when polling, and propagate failed assignments instead of reporting success |
| Review of the failing release path | Next build number trusted one version string and reset malformed results to zero | Read all build pages, choose the numeric maximum, reject malformed versions and unexpected/repeated pagination links |
| Repeated invalid-signature upload failures | IPA packaging ignored `codesign --verify` failures | Stop packaging when signature verification fails |
| Every available CI log warns about checkout's deprecated Node 20 runtime | Both jobs used `actions/checkout@v4` | Pin official checkout v5 at `fbc6f3992d24b796d5a048ff273f7fcc4a7b6c09`, using Node 24 |
| Current CI tested pure helpers but did not compile their full iOS source context | iOS integration errors could escape those tests | Type-check the nine contact/photo engine files against the iOS simulator SDK without launching a simulator |

Polling also searched only the latest five builds, which could hide an already processed target. An offline test reproduces this unnecessary wait; explicit targets now use Apple's documented `filter[version]`.

The numeric build-selection defect was found while inspecting the release path;
the historical 409 response alone does not establish that it caused a collision.
Similarly, early preflight checks prevent wasted archives but do not provision
missing credentials or certify profile expiry/bundle suitability. The real
signing/upload pipeline was not run.

The backend FoundationModels macro failures in the copied repository-sync log
refer to another repository/toolchain snapshot. Historical AppIntents metadata
and XCUIAutomation parsing warnings were recorded; no current app-runtime failure
was demonstrated. The unavailable design credential still prevents the old
private-dependency CI approach; this change adds helper type checking, not a full
application build.

## Validation

The exact release source set passed 30 Python/native-helper tests and 16
MeisterKit tests, plus iOS helper type checking and shell syntax checks. New
tests reproduce API false-success behavior, missing prerequisites, missing
request deadlines, wrong build-number selection, and pagination failures using
fake tools/responses. All release tests run offline and send no invitations,
messages, archives, or uploads. Existing auto-ship/notification opt-in tests
remain in place.

Run locally:

```sh
python3 -m unittest discover -s scripts/tests -p 'test_*.py' -v

bash scripts/check-ios-helpers.sh
```

`ASC_ISSUER_ID`, and `ASC_KEY_PATH` configure API signing. `MEISTER_APP_PROFILE`,
